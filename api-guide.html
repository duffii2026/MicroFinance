MFS Developer API Guide

Follow these steps to create a scoped key, connect to the local API, and read or write records across the six MFS modules. Copy the examples and replace the sample values with your integration settings.

MYSQL BACKEND SCOPED BEARER KEYS SIX MODULES

Know the data boundary: the shared API stores JSON records in MySQL. The original module screens still use their existing browser storage and are not automatically synchronized with API records. Agree on a data mapping or build an explicit sync before expecting API changes to appear in the legacy screens. The API accepts JSON as provided and does not validate module-specific business rules.

Step-by-step setup

01
Confirm the local service is running

Open the dashboard at its configured address. Check the public health endpoint before connecting your integration.

curl http://127.0.0.1:8081/api/v1/health

A healthy response includes "ok": true, "database": "mysql", a service name, and a version.

02
Create an API key from the dashboard

Go to API Center → API keys. Sign in with an administrator account, enter an integration name, choose only the modules it needs, choose an expiration, then generate the key. Copy the full key immediately; it is displayed only once.

03
Store the key safely

For server-side apps, keep it in an environment variable or secret manager. A key included in browser JavaScript can be read by users who access that page. Use a trusted backend proxy for public-facing applications.

04
Set the base URL and send the bearer header

Use the address shown in API Center and include the key on each protected request.

curl "http://127.0.0.1:8081/api/v1/modules/central/collections/accounts" \
  -H "Authorization: Bearer $MFS_API_KEY" \
  -H "Accept: application/json"
05
Choose a module collection

Use one of the module IDs below, then select a collection label that your integration will consistently use. The API does not enforce a fixed collection list.

06
Agree on the data mapping

Use stable IDs for relationships between companies, gateways, accounts, people, and files. Keep the names and types consistent between the source app and MFS integration.

07
Connect related files and handle errors

Upload files with their module and record ID, save the returned file ID, and use the status table below to decide whether to correct a request or check service/key configuration.

Authentication and reusable JavaScript client

Record and file routes accept either an administrator/user browser session or a scoped API key. External integrations should use a bearer key. API keys cannot log into the dashboard, change a user password, or administer other keys.

const MFS_BASE_URL = process.env.MFS_BASE_URL ?? "http://127.0.0.1:8081/api/v1";
const MFS_API_KEY = process.env.MFS_API_KEY;

async function mfsRequest(path, options = {}) {
  const response = await fetch(`${MFS_BASE_URL}${path}`, {
    ...options,
    headers: {
      Accept: "application/json",
      Authorization: `Bearer ${MFS_API_KEY}`,
      ...(options.body ? { "Content-Type": "application/json" } : {}),
      ...options.headers,
    },
  });
  const body = await response.json();
  if (!response.ok) {
    throw new Error(`MFS ${response.status}: ${body.error ?? "Request failed"}`);
  }
  return body;
}

The API keys page records the key prefix, selected modules, creator, expiration, last-used time, and revocation status. It never returns the full secret after initial creation.

Read and write records

Each item is stored as one JSON object under a module and collection. Listing returns {"items":[...]}. Reading a single record returns id, data, createdAt, and updatedAt. Create/update/delete changes are written to the audit log. An update replaces the entire payload, so send all fields you want to keep.

ActionMethodPath
Module informationGET/modules/{module}
List recordsGET/modules/{module}/collections/{collection}
Read recordGET/modules/{module}/collections/{collection}/{id}
Create recordPOST/modules/{module}/collections/{collection}
Replace recordPOST/modules/{module}/collections/{collection}/{id}
Delete recordDELETE/modules/{module}/collections/{collection}/{id}
const collection = "/modules/companies/collections/companies";

// Create
const created = await mfsRequest(collection, {
  method: "POST",
  body: JSON.stringify({ name: "Example Company", status: "Active", country: "KH" }),
});

// Read one
const record = await mfsRequest(`${collection}/${created.id}`);

// Replace the complete JSON payload
await mfsRequest(`${collection}/${created.id}`, {
  method: "POST",
  body: JSON.stringify({ name: "Example Company", status: "Reviewed", country: "KH" }),
});

// Delete
await mfsRequest(`${collection}/${created.id}`, { method: "DELETE" });

Module-by-module mapping

The module screens use different business records. These notes come from each system’s workflows and current data shapes; collection names below are recommended integration labels, not fixed server-side schemas.

Central Database MM1-01 · central

Financial registers, people, companies, gateways, merchant and operating accounts, references, currency rates, systems, uploads, and snapshots.

Recommended collectionspeoplecompaniesgatewaysmerchant-accountsaccountsratesreferencesLegacy account registers include mac, mca, pc, skac, and skap; agree whether to preserve or normalize those names.

CPA Control System MM1-02 · cpa

Bank/payment accounts, balances and status history, people and agent assignments, salary/commission statements, uploads, snapshots, and audit activity.

Suggested collections: accounts, people, agents, pay-statements, uploads, snapshots, audit.Possible account fields: bank, accountName, accountNumber, balance, status, project, holder, personId, history, updatedAt.

Account Access Credentials MM1-03 · credentials

Linked accounts and access entries, access type/status, staff permissions, documents, memos, and change history.

Legacy buckets include accounts, access, users, settings, hist, log, docs, docdata, and memos. Treat credential values as sensitive and tightly scope access.

Payment Gateways MM1-04 · gateways

Gateway configuration, merchants, locations, CPA mapping rules, contracts/rates, memos, and files.

Recommended collections: gateways, merchants, locations, rules, contracts, rates, memos, documents. Link merchant records using stable gateway IDs.

Communication Channel MM1-05 · communications

Channel/contact records with type, address, project, purpose, owner, linked service, status, sheet/group number, notes, and date added.

Suggested collections: channels, users, settings, log.

Company Database MM1-06 · companies

Company profiles, ownership/contact details, registrations, linked accounts/merchant records, files, memos, and history.

Suggested collections: companies, users, history, log, documents, memos. Preserve company IDs in related records.

Important: for example, /modules/cpa/collections/accounts creates a MySQL JSON collection for this API. It does not read or update the CPA screen’s current browser storage. Build explicit synchronization if both interfaces must show the same data.

Upload, list, and download files

Uploads accept multipart form fields file, module, and optional recordId. Maximum upload size is 25 MB. API key module scopes apply to uploads, metadata listing, and downloads.

const form = new FormData();
form.append("file", fileInput.files[0]);
form.append("module", "companies");
form.append("recordId", companyId);

const response = await fetch(`${MFS_BASE_URL}/files`, {
  method: "POST",
  headers: { Authorization: `Bearer ${MFS_API_KEY}` },
  body: form,
});
const uploadedFile = await response.json();
// Save uploadedFile.id in the related record.

Routes: GET /files?module=companies&recordId={id} lists metadata; GET /files/{fileId} returns the file content.

API-key administration

These routes require an administrator’s signed-in browser session. API keys themselves cannot manage keys.

MethodPathUse
GET/admin/api-keysList metadata and status; secrets are never returned.
POST/admin/api-keysCreate a key; full apiKey appears once.
PATCH/admin/api-keys/{id}Change name, module scopes, and optionally expiration.
DELETE/admin/api-keys/{id}Revoke key access immediately.
{
  "name": "Finance reporting integration",
  "modules": ["central", "companies"],
  "expiresInDays": 90
}

// Use null for no expiration.
// During PATCH, omit expiresInDays to retain the existing expiry.

Keys are hashed in MySQL. The API Center displays each key’s prefix, module scopes, creator, expiry, last use, and revocation status.

Browser integrations and CORS

Server-to-server integrations do not need CORS. A browser app hosted on a separate local development origin must be on the API’s allowlist. The default list includes http://localhost:3000 and http://127.0.0.1:3000.

To use another trusted local development origin, set MM1_CORS_ORIGINS in .env to a comma-separated list, then restart the MFS server. Do not put a long-lived API secret in public browser code; use a backend relay for user-facing apps.

MySQL and local storage

records stores JSON grouped by module and collection. files stores metadata while content is kept in the local files folder. users holds salted PBKDF2 password hashes. api_keys holds key hashes, scopes, and lifecycle metadata. audit_log records API changes and key administration; settings stores local service settings.

The local service initializes its InnoDB tables on startup. MySQL 8.0+ is recommended. The current JSON API does not impose foreign-key relationships or module-specific validation; the integrating application should validate its input and preserve consistent identifiers.
