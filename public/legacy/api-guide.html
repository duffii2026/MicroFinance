MFS Developer API Guide

Follow these steps to create a scoped key, connect to the local API, and read or write records across all 19 MFS modules. Copy the examples and replace the sample values with your integration settings.

MYSQL BACKEND SCOPED BEARER KEYS 19 MODULES

Know the data boundary: every module has its own MySQL database, user list, and session cookie. MM1 and MM4 screens sync their module state to that module’s browser-state collection; MM2 React screens use their module’s records collection. Signing in to one module does not sign in to another or grant access to its data.

Step-by-step setup

01
Confirm the local service is running

Open the dashboard at its configured address. Check the public health endpoint before connecting your integration.

curl http://127.0.0.1:8081/api/v1/health

A healthy response includes "ok": true, "database": "mysql", a service name, and a version.

02
Create an API key from the dashboard

Go to API Center → API keys. Sign in with an administrator account, enter an integration name, choose only the modules it needs, choose an expiration, then generate the key. Copy the full key immediately; it is displayed only once.

03
Store the key safely

For server-side apps, keep it in an environment variable or secret manager. A key included in browser JavaScript can be read by users who access that page. Use a trusted backend proxy for public-facing applications.

04
Set the base URL and send the bearer header

Use the address shown in API Center and include the key on each protected request.

curl "http://127.0.0.1:8081/api/v1/modules/central/collections/accounts" \
  -H "Authorization: Bearer $MFS_API_KEY" \
  -H "Accept: application/json"
05
Choose a module collection

Use one of the module IDs below, then select a collection label that your integration will consistently use. The API does not enforce a fixed collection list.

06
Agree on the data mapping

Use stable IDs for relationships between companies, gateways, accounts, people, and files. Keep the names and types consistent between the source app and MFS integration.

07
Connect related files and handle errors

Upload files with their module and record ID, save the returned file ID, and use the status table below to decide whether to correct a request or check service/key configuration.

Authentication and reusable JavaScript client

MM1 and MM4 keep the sign-in screens and user data included in each module. Every MM2 module has its own MySQL user list and sign-in session; logging into one MM2 module does not sign you into another. New MM2 modules start with username admin and password admin. Change the password inside each module. External integrations should use scoped bearer keys, which are separate from user logins.

MM2 module login endpoints

These routes use the exact MM2 module API ID. Module login sets an HTTP-only cookie scoped to that module.

ActionMethodPath
Sign inPOST/modules/{module}/auth/login
Check module loginGET/modules/{module}/auth/session
Sign outPOST/modules/{module}/auth/logout
Change this module passwordPOST/modules/{module}/auth/password
Manage this module’s usersGET, POST, PATCH, DELETE/modules/{module}/auth/users
const MFS_BASE_URL = process.env.MFS_BASE_URL ?? "http://127.0.0.1:8081/api/v1";
const MFS_API_KEY = process.env.MFS_API_KEY;

async function mfsRequest(path, options = {}) {
  const response = await fetch(`${MFS_BASE_URL}${path}`, {
    ...options,
    headers: {
      Accept: "application/json",
      Authorization: `Bearer ${MFS_API_KEY}`,
      ...(options.body ? { "Content-Type": "application/json" } : {}),
      ...options.headers,
    },
  });
  const body = await response.json();
  if (!response.ok) {
    throw new Error(`MFS ${response.status}: ${body.error ?? "Request failed"}`);
  }
  return body;
}

The API keys page records the key prefix, selected modules, creator, expiration, last-used time, and revocation status. It never returns the full secret after initial creation.

Read and write records

Each item is stored as one JSON object under a module and collection. Listing returns {"items":[...]}. Reading a single record returns id, data, createdAt, and updatedAt. Create/update/delete changes are written to the audit log. An update replaces the entire payload, so send all fields you want to keep.

ActionMethodPath
Module informationGET/modules/{module}
List recordsGET/modules/{module}/collections/{collection}
Read recordGET/modules/{module}/collections/{collection}/{id}
Create recordPOST/modules/{module}/collections/{collection}
Replace recordPOST/modules/{module}/collections/{collection}/{id}
Delete recordDELETE/modules/{module}/collections/{collection}/{id}
const collection = "/modules/companies/collections/companies";

// Create
const created = await mfsRequest(collection, {
  method: "POST",
  body: JSON.stringify({ name: "Example Company", status: "Active", country: "KH" }),
});

// Read one
const record = await mfsRequest(`${collection}/${created.id}`);

// Replace the complete JSON payload
await mfsRequest(`${collection}/${created.id}`, {
  method: "POST",
  body: JSON.stringify({ name: "Example Company", status: "Reviewed", country: "KH" }),
});

// Delete
await mfsRequest(`${collection}/${created.id}`, { method: "DELETE" });

Upload, list, and download files

Uploads accept multipart form fields file, module, and optional recordId. Maximum upload size is 25 MB. API key module scopes apply to uploads, metadata listing, and downloads.

const form = new FormData();
form.append("file", fileInput.files[0]);
form.append("module", "companies");
form.append("recordId", companyId);

const response = await fetch(`${MFS_BASE_URL}/files`, {
  method: "POST",
  headers: { Authorization: `Bearer ${MFS_API_KEY}` },
  body: form,
});
const uploadedFile = await response.json();
// Save uploadedFile.id in the related record.

Routes: GET /files?module=companies&recordId={id} lists metadata; GET /files/{fileId}?module=companies returns that module’s file content.

Browser integrations and CORS

Server-to-server integrations do not need CORS. A browser app hosted on a separate local development origin must be on the API’s allowlist. The default list includes http://localhost:3000 and http://127.0.0.1:3000.

To use another trusted local development origin, set MM1_CORS_ORIGINS in .env to a comma-separated list, then restart the MFS server. Do not put a long-lived API secret in public browser code; use a backend relay for user-facing apps.

MySQL databases

The configured database (for example, mm1_microfinance) stores MFS workspace accounts, API keys, and service settings. Every module has a separate database named {MM1_DB_NAME}_{module}, such as mm1_microfinance_central and mm1_microfinance_mm2_inventory. A module database contains only that module’s records, files metadata, users, sessions, and audit log.

On first startup, MFS copies existing module rows from the former shared database and keeps those original rows as a rollback copy. New changes are written to the module database only. Docker provisions these databases during MySQL initialization. MySQL 8.0+ is recommended.
